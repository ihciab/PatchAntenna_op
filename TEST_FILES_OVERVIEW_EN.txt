1. Overview
======================================================================

Current root-level test scripts:

1. test_clean_parametric_segmentation_validation.py
   Evaluates parametric segmentation quality on clean_parametric_dataset_50.
   Focuses on VTracer semantic segmentation vs GT: breakpoint positions, segment types, and effective parameter count.

2. test_curve_fit_metamaterial_antenna.py
   A broad experimental test bench for metamaterial/antenna image processing, contour extraction, curve fitting, and method comparison.
   Covers BSpline, NURBS, OptimizedNURBS, OptimizedBS, and related evaluation tools.

3. test_curve_fit_validation_dataset.py
   Evaluates curve fitting methods on validation_dataset.
   Similar in spirit to test_curve_fit_metamaterial_antenna.py, but aimed at batch validation samples.

4. test_edge_detect_validation_dataset.py
   Evaluates edge detection methods on validation_dataset.
   Compares original edge extraction, geometry-aware edge extraction, and GT-derived edges.

5. test_vtracer_centerline_system.py
   Pytest smoke/regression entry point.
   It does not implement parameterization itself; it calls test_vtracer_validation_dataset.run_batch to verify that the VTracer centerline system runs.

6. test_vtracer_validation_dataset.py
   Full validation-dataset test driver for VTracer centerline parameterization.
   Focuses on skeleton centerlines, semantic segmentation, line/arc/spline fitting, SVG, and metrics.

2. test_clean_parametric_segmentation_validation.py
======================================================================

What it tests:
- The centerline semantic parameterization flow in vtracer_python.py.
- Segmentation accuracy on clean_parametric_dataset_50.
- The experimental optimized_bs_vtracer branch: OptimizedBSplineFitter first, then VTracer semantic segmentation.

This is not the low-level algorithm implementation. It is a segmentation evaluator.

Core flow:
1. Read clean_parametric_dataset_50/summary.json.
2. For each sample, read image and GT JSON.
3. Build TraceConfig.
4. Call VTracerPython.to_svg().
5. Read predicted primitives from intermediates/component_xxxx/semantic_debug.json.
6. Compare prediction against GT:
   - Are segmentation boundaries aligned?
   - Does the line / arc / spline type sequence match?
   - Is the effective parameter count compact?
7. Write clean_parametric_segmentation_report.json.
8. Optionally write per-sample *_segmentation_result.png files.

Main metrics:
- breakpoints_mae_ratio
  Normalized mean distance from GT breakpoints to nearest predicted breakpoints. Lower is better.

- breakpoints_count_error
  Segment count difference abs(gt - pred). Lower is better.

- type_lcs_score
  LCS similarity between predicted and GT segment type sequences. Higher is better.

- effective_params_pred / effective_params_gt
  Predicted effective parameter count vs GT heuristic effective parameter count.

- parsimony_score
  Compactness score.

- param_score
  Combined score: boundaries + types + compactness.

Important functions:
- _eval_single()
  Single-sample evaluation entry.

- run_eval()
  Batch evaluation entry.

- run_eval_optimized_bs_vtracer()
  Experimental entry: run optimized_bs first, then pass the fitted polyline seed into VTracer.

- diff_segmentation_reports()
  Compare two existing reports without rerunning evaluation.

Common commands:

    D:\Python\python.exe test_clean_parametric_segmentation_validation.py

Run only the first 10 samples without PNG output:

    D:\Python\python.exe test_clean_parametric_segmentation_validation.py --max-samples 10 --no-png

Run the new experimental pipeline:

    D:\Python\python.exe test_clean_parametric_segmentation_validation.py --pipeline optimized_bs_vtracer --max-samples 10

Compare two reports:

    D:\Python\python.exe test_clean_parametric_segmentation_validation.py --diff-report baseline.json tuned.json

Main inputs:
- clean_parametric_dataset_50/summary.json
- clean_parametric_dataset_50/images/*.png
- clean_parametric_dataset_50/gt/*.json

Main outputs:
- clean_parametric_eval_output/clean_parametric_segmentation_report.json
- Per-sample SVG, metrics, and visualization PNG.
- The optimized_bs_vtracer branch also writes optimized_bs_seed_polyline.npy and optimized_bs_seed_meta.json.

3. test_curve_fit_metamaterial_antenna.py
======================================================================

What it tests:
- Image generation, preprocessing, curve fitting, and method comparison for metamaterial/antenna structures.
- It covers traditional and optimized fitting methods:
  - ImageInitializer
  - BSplineContour
  - NURBSpineContour
  - OptimizedBSplineFitter
  - OptimizedNURBSFitter
  - CurveEvaluator
  - GeometryAwareMetrics
  - SegmentExtractor
  - ColorDetector
  - Curves2Components

This file is more of a comprehensive experiment bench than a narrow unit test.

Core classes:
- MetamaterialAntennaTestGenerator
  Generates synthetic images and GT geometry.
  It can create rectangular patches, circular patches, rings, slots, arc slots, curve-line combinations, FSS units, antenna structures, and more complex/fractal patterns.

- MetamaterialAntennaTester
  Runs image processing and compares fitting methods.
  It executes multiple methods, computes metrics, and generates visualizations/reports.

Core flow:
1. Generate or read a test image.
2. Use ImageInitializer for centering, edge extraction, and preprocessing.
3. Run multiple curve fitters:
   - BSplineContour
   - NURBSpineContour
   - OptimizedNURBSFitter
   - OptimizedBSplineFitter
4. Optionally run color detection.
5. Optionally map curves to material/components with Curves2Components.
6. Compute contour counts, errors, semantic accuracy, and parameterization summaries.
7. Write comparison figures and JSON reports.

Main purpose:
- Check how well different curve fitting methods work on metamaterial/antenna geometry.
- Compare B-spline, NURBS, optimized B-spline, and optimized NURBS fitting quality.
- Evaluate whether extracted curves are suitable for later parameterization or CST modeling.

Common commands:

    D:\Python\python.exe test_curve_fit_metamaterial_antenna.py

Specify output directory:

    D:\Python\python.exe test_curve_fit_metamaterial_antenna.py --output test_metamaterial_output

Test a specific image:

    D:\Python\python.exe test_curve_fit_metamaterial_antenna.py --image path\to\image.png

Generate/use validation data:

    D:\Python\python.exe test_curve_fit_metamaterial_antenna.py --generate-validation

Main inputs:
- Built-in generated metamaterial/antenna examples.
- A user-specified external image.
- Optional validation_dataset.

Main outputs:
- Method comparison images.
- Fitting visualizations.
- JSON reports.
- Per-method statistics tables.

Note:
- This script imports NURBS-related modules. If geomdl is missing, some NURBS/OptimizedNURBS paths may fail.
- If the current task is VTracer parameterization, this is usually not the first file to modify; it mainly provides traditional/optimized curve-fitting experiments.

4. test_curve_fit_validation_dataset.py
======================================================================

What it tests:
- Curve fitting quality on validation_dataset.
- It targets existing validation samples rather than generated single metamaterial/antenna images.

It follows the structure of test_curve_fit_metamaterial_antenna.py, but is more batch-evaluation oriented.

Core class:
- ValidationDatasetTester

Core flow:
1. Read validation_dataset/summary.json.
2. Filter samples by complexity or index range.
3. Read each sample image and GT.
4. Use ImageInitializer for preprocessing.
5. Run multiple fitting methods on the same image:
   - BSplineContour
   - NURBSpineContour
   - OptimizedBSplineFitter
   - OptimizedNURBSFitter
6. Evaluate results with CurveEvaluator / GeometryAwareMetrics / SegmentExtractor.
7. Generate per-sample comparison visualizations.
8. Write summary report.

Main purpose:
- Compare different curve fitting algorithms on a standard validation set.
- Observe fitting stability across different geometry complexity levels.
- Provide batch evaluation evidence for improving traditional curve fitters.

Common commands:

    D:\Python\python.exe test_curve_fit_validation_dataset.py

Specify dataset and output directory:

    D:\Python\python.exe test_curve_fit_validation_dataset.py --dataset validation_dataset --output validation_curve_fit_output

Run only part of the dataset:

    D:\Python\python.exe test_curve_fit_validation_dataset.py --max-samples 20

Filter by complexity:

    D:\Python\python.exe test_curve_fit_validation_dataset.py --complexity simple

Main inputs:
- validation_dataset/summary.json
- validation_dataset images and GT.

Main outputs:
- Per-sample method comparison images.
- Curve fitting report JSON.

7. test_vtracer_validation_dataset.py
======================================================================

What it tests:
- The full VTracer centerline parameterization system on validation_dataset.
- It is more complete and heavier than test_vtracer_centerline_system.py.

Core flow:
1. Read validation_dataset/summary.json.
2. Build TraceConfig for each sample.
3. Call VTracerPython.to_svg().
4. Inside VTracer:
   - binarization
   - centerline skeletonization
   - skeleton path ordering
   - resampling
   - keypoint detection
   - dynamic-programming semantic segmentation
   - line / arc / spline fitting
   - SVG and metrics output
5. Read metrics.
6. Build batch_summary.
7. Write overall visualization, worst-case dashboard, and top-error reports.

Main metrics:
- semantic_segment_count
- line / arc / spline segment counts
- keypoints
- rmse_px
- mean_error_px
- max_error_px
- metrics_skipped
- skip_rate

Notes:
- GT outer-contour semantic segment count is only used as a complexity reference.
- Centerlines do not necessarily correspond one-to-one with GT outer contours.
- For strict GT breakpoint/type alignment, use test_clean_parametric_segmentation_validation.py instead.

10. 2026-05-21 FSS Parameterization to CST Pipeline Maintenance Log
======================================================================

This section records recent engineering changes to the FSS/antenna image
cleanup, geometry parameterization, CST reconstruction, and simulation pipeline.
For future maintenance, every change to the pipeline, parameterization, CST
reconstruction, or related tests should append an update here and in
TEST_FILES_OVERVIEW_CN.txt.

Main files involved:
- fss_parameterized_cst_pipeline.py
  End-to-end pipeline: read Instance JSON / inline editor config, clean the FSS
  layer image, parameterize repair_fig.png, then call parameterized_json_to_cst.py
  for CST modeling and simulation.

- geometry_driven_parameterizer.py
  Geometry-primitives backend. It consumes NewParams/VTracer centerlines,
  uses B-spline only as an intermediate representation, and exports compact
  line / arc / spline primitives plus sampled fallback points.

- parameterized_json_to_cst.py
  CST reconstruction entry. It prefers components[*].primitives when present,
  and falls back to resampled_points / fallback_points when primitives are not
  available.

Current pipeline modes:
- PARAMETERIZATION_MODE = "standard"
  Stable fallback: repair_fig.png -> NewParams -> VTracer -> curve_parameterization.json.

- PARAMETERIZATION_MODE = "geometry_primitives"
  Geometry compression flow: repair_fig.png -> adaptive edge input selection ->
  VTracer centerline -> B-spline quality gate -> primitive decomposition ->
  compact JSON -> CST.

Change summary:
1. Kept standard as the safety fallback.
   fss_parameterized_cst_pipeline.py falls back to standard if the experimental
   geometry path fails. geometry_primitives can also internally return the
   standard_NewParams_CurveParameterizer result when topology is unsafe.

2. Added topology protection.
   geometry_primitives checks VTracer centerline component count before B-spline
   and primitive compression. Current threshold:
   max_centerline_components_for_geometry = 20.
   Example: test47 produced 35 components, so compression is skipped and the
   standard JSON is used.

3. Fixed edge-mode instability.
   Forcing Canny restored old thin-edge behavior but caused inner/outer double
   edges for some line-width structures such as test48. The current solution is
   adaptive edge selection:
   - build both canny and auto/stroke_mask candidates;
   - measure how many extra Canny pixels lie within 1-3 px of auto/stroke_mask;
   - if that ratio is high, treat it as close parallel double-edge artifact and
     select auto/stroke_mask;
   - otherwise keep Canny.
   Diagnostics are written to:
   geometry_primitives/01_edges/edge_selection_diagnostics.json

4. Added a B-spline quality gate.
   Global closed B-splines can round right angles and bend long straight lines
   in FSS/antenna geometry. The current rejection thresholds are:
   - max_bspline_length_shrink_ratio = 0.08
   - max_bspline_rms_error_px = 2.0
   If rejected, the pipeline uses
   corner_preserving_linear_resample_after_bspline_reject, preserving the
   VTracer centerline geometry for primitive decomposition.

5. Increased line priority over arcs.
   To reduce cases where straight sections become arcs:
   - arc_min_sweep_deg = 28
   - arc_min_error_improvement_ratio = 0.55
   - arc_max_radius_to_chord_ratio = 4
   - arc_min_source_points = 24
   Arcs are also rejected when the competing line error is close enough.

6. Cleaned preview output.
   geometry_primitives_preview.png now keeps the image readable with colors and
   start markers only. Detailed primitive labels are saved separately:
   - geometry_primitives/06_preview/primitive_labels.json
   - geometry_primitives/06_preview/primitive_labels.csv

Important debug runs:
- run_20260521_111329
  Showed that global B-spline distorted straight geometry. Raw centerline path
  length was about 7272 px, while B-spline output was about 6045 px, a roughly
  17% shrink. Conclusion: the main error started in the B-spline intermediate,
  not in final primitive classification.

- _debug_bspline_guard_111329_b

- run_20260521_143843

2026-05-22 Maintenance Addendum: Adaptive Edge Selection False Negative Fix
- Changed file: geometry_driven_parameterizer.py.
- Symptom: run_20260522_123610 geometry_primitives_preview.png showed inner/outer multi-layer edges again.
- Cause: edge_selection_diagnostics.json had close_extra_ratio = 1.0, meaning all extra Canny pixels were close to auto/stroke_mask. However, the old rule also required canny_edge_pixels > auto_edge_pixels. In this sample auto/stroke_mask was a large foreground mask, with auto_edge_pixels = 290865 and canny_edge_pixels = 27018, so the rule missed the double-edge artifact and kept Canny.
- Fix: removed the canny_count > auto_count condition. The selector now switches to auto/stroke_mask when auto is stroke_mask, extra_canny_pixels > 0, and close_extra_ratio reaches the configured threshold.
- Validation sample: pipeline_runs/_debug_edge_select_20260522_123610. After the fix, selected_edge_mode = auto, selected_edge_representation = stroke_mask, reason = close_parallel_double_edges_detected.
- Risk: some true closely spaced coupled-line structures may also look like Canny double-edge artifacts; if that appears, add a physical-scale or stroke-width-aware criterion.

2026-05-22 Maintenance Addendum: Dense auto/stroke_mask Candidate Guard
- Changed files: geometry_driven_parameterizer.py, fss_parameterized_cst_pipeline.py.
- Symptom: in run_20260522_124630, _candidate_auto/repair_fig_edges.png was not an edge image; it was a filled foreground mask with about 26.6% white pixels.
- Cause: after removing canny_count > auto_count, a high close_extra_ratio alone could select auto/stroke_mask even when that candidate was an invalid dense filled region.
- Fix: added validity checks for auto/stroke_mask: max_stroke_mask_foreground_ratio = 0.08 and max_stroke_mask_to_canny_ratio = 3.0. If exceeded, auto_stroke_mask_valid = false and the candidate cannot become the final edge input.
- Validation sample: pipeline_runs/_debug_edge_select_20260522_124630_density_guard. After the fix, selected_edge_mode = canny, auto_stroke_mask_valid = false, auto_foreground_ratio = 0.2659.
- Risk: a very thick but valid centerline mask could be rejected; if such cases appear, tune the thresholds using physical scale or image category.

2026-05-22 Maintenance Addendum: Close Parallel Double-Edge Merge Prior
- Changed files: geometry_driven_parameterizer.py, fss_parameterized_cst_pipeline.py.
- Symptom: run_20260522_125241 still showed close double-layer edges from the Canny input.
- User prior: for this patch-antenna design scope, if two straight lines are too close, treat them as the same line; otherwise that coupled-line design case is out of scope.
- Fix: when auto/stroke_mask is invalid because it is too dense, but Canny extra edges are highly close-parallel, create _candidate_canny_merged. This candidate morphologically merges nearby Canny edges and skeletonizes them back to a single-pixel centerline for VTracer.
- Parameter: close_parallel_merge_distance_px = 10.
- Additional adjustment: max_centerline_components_for_geometry changed from 20 to 30 so the merged 24 open-centerline components do not immediately trigger topology fallback.
- Validation sample: pipeline_runs/_debug_close_parallel_merge_125241. _candidate_canny_merged/repair_fig_edges.png compresses close double edges into single lines.
- Risk: this prior intentionally merges true closely spaced coupled lines. If those structures must be supported later, disable this path or reduce close_parallel_merge_distance_px.

2026-05-22 Maintenance Addendum: canny_merged Main-Structure Retention Gate
- Changed files: geometry_driven_parameterizer.py, fss_parameterized_cst_pipeline.py.
- Symptom: run_20260522_130401 geometry_primitives_preview.png showed that close-edge merging was too aggressive; the side-view main structure was compressed into too few centerlines and lost important outline information.
- Cause: _candidate_canny_merged dilates the whole Canny image and then skeletonizes it. That is useful for local double-edge repair, but on continuous side-view boundaries it can also medial-axis real outlines. The old diagnostics had canny_edge_pixels = 27018 and merged_canny_edge_pixels = 5202, only about 0.1925 retention.
- Fix: added min_merged_canny_retention_ratio = 0.50. After generating _candidate_canny_merged, the selector computes merged_canny_edge_pixels / canny_edge_pixels. If the ratio is below the threshold, canny_merged is rejected, Canny is kept, and edge_selection_diagnostics.json records merged_canny_rejected_erases_major_structure.
- Validation sample: pipeline_runs/_debug_retention_guard_130401. After the fix, selected_edge_mode = canny, merged_canny_retention_ratio = 0.3120, merged_canny_valid = false, and the main outline is preserved better than run_20260522_130401.
- Risk: falling back to Canny can still show double outlines for thin conductors. The better long-term fix is local segment clustering or local double-edge merging instead of full-image skeleton merging.

2026-05-22 Maintenance Addendum: Solid Mask Topology Branch
- Changed files: geometry_driven_parameterizer.py, parameterized_json_to_cst.py.
- Symptom: pipeline_runs/run_20260522_131935/02_parameterization/geometry_primitives/06_preview/geometry_primitives_preview.png still had wrong topology. The sample is not a thin wire; repair_fig.png contains filled metal regions and white slots. Canny creates inner/outer outlines, while skeletonizing the dense stroke mask turns the filled PEC into a medial-axis graph.
- Fix: geometry_primitives now detects dense auto/stroke_mask candidates as solid masks when the foreground ratio is at least max(max_stroke_mask_foreground_ratio * 2, 0.12). Those samples skip VTracer centerline extraction and export backend=solid_mask_topology: one closed outer boundary per filled solid plus optional holes. A pixel-level large-border-frame cleanup removes drawing frames before contour extraction.
